# Job Searching Assistant

**Русский** | [English](README.md)

Job Searching Assistant — локальная платформа для поиска вакансий и подготовки откликов с
обязательной проверкой пользователем. Она импортирует и находит вакансии, анализирует резюме,
рассчитывает объяснимое соответствие, готовит материалы и заполняет поддерживаемые браузерные
формы до контрольной точки. Реальная отправка в HeadHunter и LinkedIn по умолчанию отключена.

Текущая версия: **1.5.4**.

## Текущий релиз

- Перерасчёт соответствия разделён на быстрый **умный перерасчёт** (переиспользует кэш
  результатов LLM; без изменений возвращает готовый результат мгновенно) и **полный
  перерасчёт** — после смены модели LLM. Результаты декомпозиции и entailment кэшируются
  в Redis с ключами, учитывающими модель; entailment останавливается раньше при сильном
  подтверждении, пары (утверждение, доказательство) оцениваются **батчами** (по умолчанию
  5 пар за один вызов LLM), а простые навыки вообще не обращаются к LLM — холодные прогоны
  быстрее, повторные почти мгновенные. Классификацию entailment можно дополнительно
  направить на отдельную небольшую модель через `APP_MATCHING_ENTAILMENT_MODEL`
  (например, `qwen3:1.5b`), оставив экстракцию и декомпозицию на модели матчинга из
  вкладки «Модель».
- Модели LLM настраиваются **по назначению** во вкладке «Модель»: отдельная модель для
  **матчинга** (экстракция, декомпозиция, entailment) и отдельная для **генерации
  материалов** (сопроводительные письма, ответы на скрининг, анализ резюме). Матчинг
  использует модель материалов как запасную, пока не сохранена своя.
- Провайдер LLM адаптируется к OpenAI-совместимым эндпоинтам, принимающим только
  форматы `text` и `json_object` (например, gateway local-code-worker): структурированные
  запросы матчинга автоматически переключаются на `json_object`, если `json_schema`
  отклоняется, — экстракция, декомпозиция и entailment продолжают работать.

- Matching v2.3 разбивает требования вакансии на отдельные утверждения и различает подтверждённые,
  частично подтверждённые, недостаточные, ошибочно обработанные и отсутствующие доказательства.
- В материалы отклика передаются те же ключевые навыки вакансии, которые показаны на карточке.
  Навык подчёркивается только при наличии в проверенных фактах кандидата: требования вакансии не
  превращаются в утверждения об опыте кандидата автоматически.
- Опциональные поиск RAG и загрузка вакансий, профилей и резюме изолированы по владельцу данных.
- Флаг **«Сразу в реранкер»** ожидает загрузку данных в RAG и подробный расчёт до показа результатов.
  Доступные внешние RAG и реранкер уточняют порядок доказательств; при их недоступности используется
  локальный hybrid fallback, а найденная вакансия не отбрасывается.
- Факты профиля можно импортировать из поддерживаемых файлов или извлечь из выбранного резюме и
  проверить до их использования в сопоставлении и сгенерированном тексте.

Полная история версий приведена в [`CHANGELOG.md`](CHANGELOG.md).

## Возможности

- локальный кабинет FastAPI и очередь проверки;
- PostgreSQL как основной источник бизнес-данных;
- Redis для координации задач и lease-механизма;
- перестраиваемый индекс сопоставления OpenSearch;
- изолированные Playwright-сессии для HeadHunter, LinkedIn, Greenhouse и настроенных сайтов;
- выбранные пользователем Anthropic, Gemini или OpenAI-совместимые модели;
- шифрование browser state, LLM-ключей и чувствительных autofill-значений;
- контролируемые fixtures для browser и end-to-end проверок.

Локально кабинет доступен по адресу `http://127.0.0.1:8000/dashboard`, а в доверенной локальной
сети — по адресу `http://192.168.1.93:8000/dashboard`; соответствующая очередь проверки использует
путь `/review`. Compose открывает в LAN только порт `8000`. PostgreSQL, Redis, OpenSearch, рабочий
стол браузера, browser worker и сервис моделей остаются привязаны к loopback. При LAN-доступе API
работает в production-режиме и требует `APP_API_KEY` или `APP_API_CLIENTS_JSON`; если ключа нет,
`scripts/setup.ps1` генерирует `APP_API_KEY` в игнорируемом локальном `.env`.

## Быстрый запуск в Windows

Нужны Windows 10/11, Docker Desktop с WSL 2, Git for Windows, не менее 8 ГБ RAM и 10 ГБ свободного
места.

```powershell
git clone https://github.com/Sa1avatus/job-searching-assistant.git
Set-Location job-searching-assistant
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1
```

Скрипт создаёт игнорируемую локальную конфигурацию, при необходимости генерирует ключи шифрования,
создаёт общую локальную Docker-сеть Worker, собирает контейнеры, применяет миграции и ждёт health
checks. Существующие Docker volumes он не удаляет.

Безопасная остановка и повторный запуск без удаления данных:

```powershell
docker compose down
docker compose --profile browser up -d --wait
```

Не запускайте `docker compose down -v`, если не хотите удалить локальные данные PostgreSQL, Redis,
OpenSearch и моделей.

## Первый запуск

1. Создайте локального пользователя в разделе **Access**.
2. При необходимости выберите LLM-провайдера и модель в **Model** — отдельно для матчинга
   и для генерации материалов.
3. Загрузите и проверьте одно или несколько резюме.
4. Сохраните пользовательские сессии сайтов в **Site sessions**, где нужна авторизация.
5. Выберите резюме и запустите поиск вакансий.
6. Проверяйте подготовленные данные и каждое внешнее действие перед подтверждением.

### Ручной импорт писем

В разделе **Все вакансии** можно импортировать переписку по откликам без подключения IMAP.
Поддерживается одновременный выбор до 100 файлов `.eml`, экспорт почтового ящика `.mbox`,
ZIP-архивы с EML-файлами или их сочетание. Общий размер загрузки ограничен 50 МБ, за один импорт
обрабатывается не более 500 сообщений. Вложенные EML-письма классифицируются отдельно, поэтому
пересланный или экспортированный отказ может обновить связанную вакансию, не смешиваясь с текстом
внешнего письма. Поддерживаются текстовые и содержащие только HTML письма; имя отправителя может
использоваться как осторожная подсказка для определения компании. Итог импорта отдельно показывает
нераспознанные и распознанные, но не привязанные к вакансиям сообщения. Исходные загруженные файлы
не сохраняются; временный файл используется только на время чтения mbox.

Поиск HeadHunter из кабинета использует сохранённую сессию. Низкоуровневый read-only adapter
может читать публичные страницы вакансий без неё, но кабинет работает иначе. Поиск LinkedIn требует
сохранённой сессии и `APP_ENABLE_LINKEDIN_APPLY=true`. Greenhouse читает публичные доски, а
браузерная подготовка всегда останавливается до отправки.

## Детальное сопоставление

Встроенный BGE-сервис требует NVIDIA-совместимого Docker, не менее 16 ГБ RAM и около 12 ГБ
дополнительного места. При первом запуске загружается несколько гигабайт:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1 -EnableDetailedMatching
```

Matching v2 по умолчанию работает в shadow mode. Основные данные остаются в PostgreSQL, индекс
OpenSearch можно перестроить.

### Коллекции RAG

Подтверждённые факты профиля, проанализированные резюме и вакансии хранятся в отдельных
owner-scoped коллекциях `profiles`, `resumes` и `vacancies`. Изменения фактов обновляют профильный
документ, а удаление резюме или пользователя удаляет соответствующие документы из RAG в режиме
fail-open: PostgreSQL остаётся авторитетным даже при недоступности внешнего сервиса.

В панели резюме кнопка **«Отправить в RAG»** позволяет явно повторить синхронизацию одного
подтверждённого резюме. Синхронизация выполняется через durable dispatcher с ограниченными
повторами; в панели видны её состояние и безопасный код последней ошибки. Повторное нажатие не
создаёт дубликат уже активной задачи. Для существующих данных доступен ограниченный owner-scoped
backfill:

```powershell
recruitment-assistant rag-backfill --user-id USER_ID --batch-size 50
```

Пока `resumes_has_more` или `vacancies_has_more` равен `true`, в следующий запуск нужно передавать
оба возвращённых курсора. Команда выводит только счётчики и курсоры, без содержимого персональных
данных. Агрегированные метрики `rag_sync_*` и `rag_delete_*` доступны на `/metrics`.

Старые matching-объяснения можно поставить на пересчёт ограниченными owner-scoped страницами:

```powershell
recruitment-assistant matching-backfill --user-id USER_ID --batch-size 50
```

Пока `has_more` равен `true`, `next_application_cursor` передаётся как `--after-application-id`.
Команда планирует только устаревшие, ошибочные или созданные до source v2 результаты. Предыдущие
оценка и объяснение остаются доступны до успешного завершения нового расчёта.

## Безопасность

- `.env`, browser state, резюме, screenshots и реальные evidence остаются локальными и игнорируются.
- Текст от модели не управляет Playwright или хранилищем напрямую.
- CAPTCHA, 2FA, чувствительные декларации, неизвестные обязательные ответы и переход на неразрешённый
  host всегда требуют участия пользователя.
- Автоматические тесты используют контролируемые fixtures и не отправляют реальные отклики.
